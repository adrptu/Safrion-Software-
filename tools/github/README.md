As regras de equipe continuam em [protocolo](../../docs/parceria/protocolo.md).

`fluxo_pr.py` automatiza abertura idempotente de draft, preflight e merge imediato
por SHA. Usa `gh` autenticado **com a identidade existente do executor**, sem ler
ou guardar tokens. Não instala ferramentas, cria contas, muda ruleset, faz push,
atualiza branch, habilita auto-merge, resolve discussões ou emite pareceres.
O merge manual pelo revisor segue [DEC-1810-01](../../docs/DECISIONS.md#dec-1810-01--integração-manual-pelo-revisor) e AGENTS.md §3.
Essa autorização não dispensa checks, pareceres, proteção ou confirmação do destino.
Não é serviço de plantão. O agente continua sendo responsável pelo acionamento e
por examinar a evidência. Não executa textos de PR no shell.

Use um checkout isolado de um **SHA já revisado** contendo helper, política e
normalizador; confira o SHA e a ausência de alterações antes de usar credenciais:

```sh
git worktree add --detach /tmp/safrion-fluxo SHA_REVISADO
git -C /tmp/safrion-fluxo rev-parse HEAD
git -C /tmp/safrion-fluxo status --porcelain
cd /tmp/safrion-fluxo
```

Substitua `SHA_REVISADO` pelo commit completo identificado nos pareceres e compare
com `rev-parse`. Saída não vazia de `status` exige outra cópia limpa, sem apagar
trabalho. Todos os comandos abaixo partem dessa cópia, nunca da branch de uma
candidata ainda não revisada. No primeiro merge do PR #38, o integrador Claude
usa a API/interface autorizada existente, com o mesmo gate e readback; não depende
da ferramenta que ainda está sendo incorporada.

## Abrir uma candidata

Depois do push autorizado, indique o commit completo e o corpo salvo em arquivo:

```sh
python3 tools/github/fluxo_pr.py abrir --branch codex/minha-fatia \
  --head-sha COMMIT_COMPLETO --title 'Resultado da mudança' --body-file /tmp/pr.md
```

Busca por repositório, base e branch. Se já existir, retorna o mesmo PR sem
sobrescrever edição concorrente. Um PR fechado/integrado exige outra branch.
POST incerto provoca leitura de volta, nunca novo POST automático. Resultado
ausente ou ambíguo bloqueia. `abrir` cria somente draft; tornar pronto é decisão
do responsável após examinar os aceites, pelo canal existente.

## Recibos reais, sem simulação de identidades

Cada agente registra **um objeto JSON na conversa do PR**, a partir de sua
execução/análise real. Texto citado, bloco de código ou simples ACK não vale.
Depois do objeto, só espaços ou o rodapé exato do Claude são permitidos:
`\n\n---\n_Generated by [Claude Code](https://claude.ai/code)_`.
O hash cobre o corpo inteiro, inclusive o rodapé. Chaves duplicadas são recusadas.
O autor apresenta evidência e o outro implementador (Codex/Claude) apresenta a revisão independente e integra, conforme AGENTS §2/§3 e DEC-0910-02. Gemini contribui com contraprova quando pertinente ao risco/aceite da entrega; não é consulta obrigatória para toda operação mecânica.
Exemplo de forma (valores ilustrativos, não constituem recibo):

```json
{
  "schema": "safrion-review-v1",
  "repo": "adrptu/Safrion-Software-",
  "pr": 123,
  "head_sha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "base_sha": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "author": "codex",
  "agent": "claude",
  "role": "reviewer",
  "model": "modelo real registrado pelo executor",
  "verdict": "pass",
  "blocking_findings": [],
  "raw_evidence_analyzed": true,
  "executions": [{
    "requester": "claude", "executor": "executor identificado",
    "result": "comando, resultado e alcance analisados",
    "evidence_url": "https://github.com/adrptu/Safrion-Software-/issues/1#issuecomment-123",
    "sha256": "cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc"
  }],
  "limits": ["limites pertinentes da prova"]
}
```

O coordenador reúne no `pedido.json`: `repo`, `pr`, `head_sha`, `base_sha`,
`author`, `integrator` e `receipts` (dois objetos, ou três com contraprova, com `comment_id` e
`sha256` do corpo UTF-8 exato retornado pela API). Agentes permitidos: `codex`,
`claude`, `gemini`; papéis únicos: `author`, `reviewer`, `counterproof`. Autor e integrador são Codex/Claude distintos; o integrador é o revisor. Se o aceite exigir Gemini, incluir `counterproof_required: true` no pedido (booleano; padrão false). A decisão de pertinência vem do contrato da entrega, conferido pelo integrador; o helper não interpreta o risco do diff. Parecer já emitido para a candidata, inclusive Gemini, não pode ser omitido: seu último recibo precisa ser selecionado e favorável, mesmo com `counterproof_required: false`.
O comentário dedicado de parecer favorável/retirada usa o formato exato de
`revisao_codex.py`: não substitui os recibos JSON nem os checks. O último ato para
o HEAD (por atualização e ID) deve existir e ser favorável; ausência/exclusão ou retirada bloqueia mesmo diante
de um check ainda verde. Texto adicional ou citado não recebe essa exceção.
Um recibo estruturado posterior para a mesma candidata substitui o anterior,
inclusive se bloquear. A conversa inteira é paginada. Comentário autorizado após
o primeiro recibo selecionado que cite o schema ou HEAD atual e esteja fora do
formato bloqueia como possível revogação; o integrador precisa resolver o texto e
obter os recibos atuais depois da consolidação. Outras narrativas continuam
exigindo leitura humana/do agente integrador. CONTRIBUTOR não recebe autorização
de relator por esta regra. PR nos recibos é um inteiro, não texto ou decimal.
Mesmo com JSON válido, um comentário posterior desse schema que cite o PR ou
HEAD atual e tenha agente desconhecido/ausente ou campos de candidata divergentes
bloqueia como recibo/revogação ambíguo. Isso inclui outra base ou HEAD no mesmo PR:
o integrador esclarece se é histórico ou revogação e reúne recibos atuais depois.
Uma referência a outro PR e outro HEAD não interfere. A regra conservadora evita
interpretar um erro de preenchimento como ausência de revogação.
Uma mudança de HEAD/base ou edição do recibo invalida o pedido; reaproveitar
provas pertinentes exige novo parecer explícito sobre a composição atual.

**Limite de confiança:** a conta GitHub compartilhada não autentica qual IA
atuou. O helper verifica forma, origem do comentário, hashes e candidata; não
certifica que a IA leu/executou o que declarou, nem analisa semanticamente logs,
URLs ou todos os achados. O integrador independente confere isso nos canais reais
antes de montar o pedido. O SHA da evidência é rastreio, não download/verificação
automática do conteúdo. Não chamar esses recibos de aprovações nativas.

## Conferir e integrar

```sh
python3 tools/github/fluxo_pr.py verificar --pedido /tmp/pedido.json
python3 tools/github/fluxo_pr.py integrar --pedido /tmp/pedido.json --head COMMIT_COMPLETO
python3 tools/github/fluxo_pr.py integrar --pedido /tmp/pedido.json --head COMMIT_COMPLETO --executar
```

Os dois primeiros comandos só fazem leituras, incluindo GraphQL via POST.
O terceiro coleta de novo, valida e faz um
único PUT com SHA esperado. Autor não integra próprio PR. O integrador real deve
ser o agente indicado, não um nome fornecido pelo autor. `verificar --snapshot`
serve somente para diagnóstico/teste: retorna `eligible-offline` e exit 1 mesmo
quando a lógica passa, sem argumentos de merge. Não autentica o arquivo nem
alimenta a mutação `integrar`. A função pura `avaliar` também não autentica seus
dados. Snapshot vence em 120 segundos; nenhuma decisão salva autoriza uma retomada.

**Transporte atual:** a consulta de threads exige GraphQL de leitura e paginação
completa. No executor remoto Claude ela respondeu 403 em 04/10/2026; ali o comando
`integrar` permanece bloqueado. A rota observada `ccr/review_threads` não tem
contrato/completude demonstrados e não foi adotada. Não substituir por comentários
REST, que não comprovam resolução. No fluxo por conector oficial, o integrador
obtém leituras autenticadas equivalentes, completas e recentes, podendo delegar
a leitura de threads ao Codex e analisar seu bruto; um arquivo isolado não serve
de aceite. A coleta completa e a leitura delegada vencem em 120 segundos;
recomeçar se o repasse exceder esse prazo, sem usar dez minutos como tolerância.
Erro, truncamento ou falta de prova de completude bloqueiam. Depois,
o próprio integrador independente faz a chamada autorizada com SHA esperado e
confere o readback abaixo. Isso é uma operação do executor, não ativação do CLI
nesse ambiente nem prova de independência do Mac.

Para diagnóstico, o snapshot contém `collected_at` (início UTC da coleta),
`identity` (`user`), `pr`, `base_sha` (ref main), `compare` (base…head), `ruleset`,
`checks`, `reviews`, `comments` e `receipts` (os comentários por ID textual).
`checks`, `reviews` e `comments` são coleções integralmente paginadas; só então
`comments_complete=true`. `threads` contém `isResolved` booleano e só recebe
`threads_complete=true` depois de concluir todas as páginas do canal oficial.
Essas marcas declarativas não autenticam um arquivo de snapshot.

Gate: PR aberto, pronto, da mesma origem, base main atual incorporada, estado
clean; política ao vivo igual à versão revisada sem bypass; todos os checks
obrigatórios executados com success no HEAD/app exatos; evidência do autor e parecer do revisor independente (mais contraprova quando exigida ou já emitida);
nenhuma discussão aberta ou revisão nativa solicitando alterações. Skipped,
neutral, erro, paginação incompleta e ausência de dado bloqueiam. Mudança da
política bloqueia para revisão, em vez de aceitar silenciosamente menos checks.
O gate para no primeiro impedimento; exit 0 de preflight não é recibo de merge.

O SHA do PUT impede troca de HEAD. A API não fornece compare-and-swap para base
e recibos. A base é relida antes do PUT e a proteção strict continua obrigatória;
os pais do merge são conferidos depois. Não há promessa de transação atômica
entre comentários, CI e merge. Mudança concorrente observada exige diagnóstico,
sem bypass, atualização automática da branch ou reversão automática.

Em timeout/recusa, relê o PR uma vez. Reexecutar após merge confirmado apenas
confere pais e presença em main, sem repetir PUT. Só uma resposta `merged:true`
do PUT desta execução, com SHA confirmado no readback, produz `merged` e
`performed_by_this_run:true`. Merge preexistente ou resultado incerto produz
`merged_observed`, `performed_by_this_run:false` e exit 1; não atribui a esta
execução o aceite ou a autoria do merge observado. O JSON resultante deve ser
preservado no PR como recibo do que foi observado/executado. O helper **lista**
os runs de push; o integrador precisa conferir cada conclusão na retomada
existente. Ausência de run é pendência, não CI verde. Exit 0 de merge confirma a
operação e não o sucesso da CI posterior.
Merge não equivale a aceite de HML ou autorização de produção.

## CI e ativação

O helper e testes entram pelos checks existentes; nenhum workflow novo ou
GITHUB_TOKEN de escrita. GitHub informa que esse token exige aprovação para
certos eventos de PR e não dispara os pushes seguintes. Usar a identidade
existente evita introduzir essa dependência, mas **cada execução real** deve
registrar merge, SHA, ator e CI pós-merge. O bootstrap descrito acima continua
sendo do Claude, após parecer Codex/Claude/Gemini e checks: o autor não o autoaprova.
Os drafts #32–#37 não ganham aceite por esta entrega. A correção de imagens já
preparada em outro PR continua sendo dependência; não repetir pesquisa de digest.

Teste local sem rede: `python3 -m unittest discover -s tools/ci -p test_fluxo_pr.py`.
